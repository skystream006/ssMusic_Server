## HTTPS and server wiring

`loadHttpsOptions` in `/home/runner/work/ssMusic_Server/ssMusic_Server/src/tls.js` (lines 16–69) loads configured key/cert files without regenerating them. Otherwise it stores generated files under `/home/runner/work/ssMusic_Server/ssMusic_Server/data/tls` for this working directory (container: `/app/data/tls`). Generated CN prefers the secondary RP hostname, then primary, then localhost; SANs include configured RP/origin hosts and loopbacks. Reuse checks CN/SAN coverage; do not promise an expiration-renewal policy the implementation does not provide. Private-key writes use mode `0600`. Local self-signing is not public browser trust.

`protectServer` and listener startup in `/home/runner/work/ssMusic_Server/ssMusic_Server/src/server.js` (lines 799–828) create separate HTTP redirect and HTTPS application listeners. HTTP returns 308 using the configured primary origin as its base. Reverse-proxy choices must preserve correct browser origin, cookie security, rate-limit identity, and reachability; **access owns middleware ordering**. If wiring changes, inspect only the relevant middleware segment (lines 92–135) and matching access tests rather than reorganizing feature routes.

## Health and timer semantics

- `/health` is an HTML SPA route, not a JSON readiness endpoint: `/home/runner/work/ssMusic_Server/ssMusic_Server/src/server.js`, `GET /health` (lines 771–773). Docker's healthcheck requests it over local HTTPS with certificate verification disabled (`/home/runner/work/ssMusic_Server/ssMusic_Server/Dockerfile`, lines 40–41); a 200 does not prove database/transcription readiness.
- `/api/health` is behind `requireAuth` and shared-access restrictions, returns live system metrics with cached aggregate media usage, and sets `Cache-Control: no-store`. It excludes the per-user map: `/home/runner/work/ssMusic_Server/ssMusic_Server/src/server.js` (lines 122–132, 760–768).
- `/home/runner/work/ssMusic_Server/ssMusic_Server/src/health.js`, `scanMediaFiles`/`createMediaCountMonitor` (lines 11–67), scans once at startup and every 24 hours; reads do not rescan, overlapping scans are skipped, and failures retain the previous successful values/timestamp. Counts use existing regular media files, exclude missing/non-media/path-escape entries, and deduplicate resolved paths across jobs (case-insensitively on Windows).
- Per-user usage attributes files to initiating owners, not contributors; a physical path shared by multiple owning jobs counts once globally and once for each owner. `songFiles` counts audio. Only the administrator route consumes `byUser`: `/home/runner/work/ssMusic_Server/ssMusic_Server/src/auth.js`, `GET /api/admin/users` (lines 517–529). Runtime supplies data; access owns disclosure.
- `getTranscriptionHealth` in `/home/runner/work/ssMusic_Server/ssMusic_Server/src/health.js` (lines 69–87) performs a two-second, manual-redirect **HEAD** probe. Any HTTP response, including redirects/4xx/5xx, is “active”; only absent configuration, network failure, or timeout is inactive. This is reachability, not successful transcription or model readiness.
- `/home/runner/work/ssMusic_Server/ssMusic_Server/src/scheduler.js`, `scheduleDailyMaintenance` (lines 3–50), computes the next **local-time 03:00**, waits for completion, and reschedules with an unreferenced timer. Execution/queue gates belong to `runMaintenanceUpdate` in `/home/runner/work/ssMusic_Server/ssMusic_Server/src/jobManager.js`.
- `scheduleLibraryBackups` in `/home/runner/work/ssMusic_Server/ssMusic_Server/src/scheduler.js` (lines 52–67) immediately polls `runDue`, then polls 60 seconds after each completion. It does not define backup due dates: `/home/runner/work/ssMusic_Server/ssMusic_Server/src/libraryBackup.js`, `nextBackupTime` (lines 11–32), uses **UTC** monthly/weekly policy owned by library-transfer. Do not apply the maintenance local clock to backups.

Do not deploy production or add validation scripts. Documentation-only changes need neither builds nor test execution.
